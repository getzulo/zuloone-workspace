# ZuloOne Workspace — правила для агента

## Что это за проект

**ZuloOne** — low-code ERP-платформа: бизнес-приложение описывается
МЕТАДАННЫМИ (справочники, документы, регистры, меню) плюс C#-скриптами,
которые платформа компилирует на лету. Из метаданных платформа сама генерит
таблицы БД, классы сущностей, REST API и весь UI (гриды, формы записей,
риббон). Ты разрабатываешь только БИЗНЕС-СЛОЙ — данные и логику предметной
области; платформенного кода здесь нет.

Этот воркспейс — бизнес-слой как файлы (модель D365FO): каждая папка верхнего
уровня — **модель** (модуль/приложение) со своим `model.json`. Модели лежат в
слоях `System(0) → Base(1) → Solution(2) → Customization(3) → User(4)`: модель
видит нижние слои и расширяет их объекты аддитивно (новые поля, обработчики
поверх, куски меню), но никогда не редактирует чужое. Зависимости между
моделями объявляются явно в `model.json` — см. скилл `zuloone-new-model`.

Воркспейс синхронизируется с работающим сервером ZuloOne **в обе стороны
live**: сохранил файл → через 2–4 секунды он применён к базе; изменил что-то
в дизайнере ZuloOne → файл переписан. Структура — json, код — .cs,
производное — не в git.

Из этого следует главное разделение труда:
- **ты пишешь**: метаданные объектов (json), бизнес-код (события, проводки,
  команды, сервисы), меню, интеграционные тесты;
- **ты НЕ пишешь**: SQL и миграции, классы сущностей, контроллеры/эндпоинты,
  UI-компоненты, EF-маппинги — всё это платформа генерит из твоих метаданных.
  Если кажется, что нужно «дописать платформу» — это задача репозитория
  платформы, не воркспейса.

Полный контракт форматов: docs/WORKSPACE.md в репозитории платформы.
Готовые рецепты: `.claude/skills/` — `zuloone-new-model`,
`zuloone-new-dictionary`, `zuloone-new-document`, `zuloone-new-register`,
`zuloone-new-service`, `zuloone-extend` (расширение чужих моделей),
`zuloone-new-test` (тесты с автооткатом), `zuloone-verify`.

## Что НЕЛЬЗЯ — жёсткие запреты

1. **`.generated/`** — производное (классы сущностей, framework-половины
   partial-скриптов, GlobalUsings). Перегенерируется каждым экспортом. Никогда
   не редактировать; читать — можно и нужно (это IntelliSense-истина о том,
   какие свойства есть у сущностей).
2. **`Core/`** — системная модель. Синк ТОЛЬКО вниз: правки её файлов
   отклоняются и переэкспортируются из базы. Ядро меняется только в исходниках
   платформы. `*.engine.cs` в `Core/TotalDrivers/` — read-only копии
   платформенных движков, для чтения.
3. **`ZuloOne.Workspace.csproj`, `.zuloone-export-manifest.json`** — служебные,
   поддерживаются экспортом.
4. **`metaId` существующих строк не менять никогда** — это идентичность объекта;
   матчинг при импорте идёт по metaId. Переименование объекта = поменять `name`
   (и имя файла/папки), metaId остаётся.
5. **Чужие модели**: не менять строки с чужим `modelId`. Расширение чужого
   объекта — только аддитивно: новое поле на чужом справочнике создаётся в СВОЕЙ
   модели (сервер завернёт его в экстеншн-агрегат `<Цель>.<Модель>`), обработчик
   поверх чужого скрипта — наследованием (`baseScriptMetaId`, цепочка расширений).
6. **Удаления файлов НЕ распространяются**: пропавший из папки объект не
   удаляется из базы (кроме пунктов `Menu/menu.json` — см. ниже). Удаление
   объектов — через дизайнер (там каскад и импакт-превью) или API.
7. **В скриптах запрещены опасные API**: файловая система, сеть, процессы,
   рефлексия в обход платформы. Политика безопасности скриптов (Enforce)
   отклонит такой код при импорте/сохранении. Всё, что нужно скрипту, доступно
   через контекст платформы (`Db`, `GetService<T>()`, типизированные сущности).
8. **Секреты** (строки подключения, пароли, токены) в воркспейс не писать —
   это git-репозиторий поставки.

## Как ПРАВИЛЬНО — конвенции

- **Структура = json, код = .cs.** Пара «`X.script.json` (привязка) + `X.cs`
  (код)» неразделима: envelope несёт scriptType/objectType/objectMetaId, кодовый
  файл — только юзер-partial.
- **Новый объект = новый файл с новым GUID** (uuid v4) в `metaId`. Внутренние
  ссылки json — по metaId (`edtMetaId`, `numberSequenceMetaId`,
  `tablePartTypeMetaId`, `referenceDictionaryMetaId`, `parentMetaId`…) — держи
  их согласованными между файлами. У каждой строки — `modelId` = metaId модели
  из `model.json` папки и её `layerId`.
- **Имена объектов и полей — PascalCase латиницей** (они же имена C#-классов,
  свойств и таблиц): `GoodsReceipt`, `WarehouseID`.
- **Подписи многоязычны инлайн**: `caption` — базовая подпись НА АНГЛИЙСКОМ,
  рядом `caption_ru`, `caption_ar`, … — переводы (это файл-форма
  MetaTranslations; язык, убранный из файла, удаляется). UI показывает
  перевод языка пользователя с фолбэком на `caption`. Ровно тот же паттерн —
  у `subtypeCaption` подтипов документа (`subtypeCaption_ru`,
  `subtypeCaption_ar`, …). `Translations/<lang>.json` остаётся для переводов
  НЕ-подписей.
- **Системные поля не пишешь ты**: у нового справочника/документа поле `ID`
  (+ `ParentId` для иерархических) создаёт сервер при импорте. Номерную серию
  для `ID` сервер тоже создаст, но лучше объявить свою (`NumberSequences/*.json`)
  и сослаться `numberSequenceMetaId`.
- **EDT-first**: ссылочные поля типизируются через EDT (`edtType: "Reference"` +
  `referenceDictionaryMetaId`), скаляры — EDT или инлайн `baseType`
  (`String`/`Integer`/`Long`/`Decimal`/`DateTime`/`Boolean`/`Guid`) с
  `length`/`precision`/`scale`. Целое — именно `Integer`: `Int` каталог типов не
  принимает, и падает не импорт, а `schema/sync` («Base type 'Int' is not in the
  catalog») — объект в базе уже есть, а таблицы под него нет.
- **Один `fieldName` — одна колонка** в пределах модели. **Имена классов
  скриптов уникальны во всём воркспейсе** — все модели попадают в один
  IDE-проект: первый обработчик объекта называется конвенционально
  (`<Имя>EventHandler`), каждое СЛЕДУЮЩЕЕ звено цепочки/расширение — со своим
  суффиксом (`<Имя>ExtEventHandler`, `<Имя>Tx_<Модель>`); рантайм найдёт класс
  по базовому типу.
- **Модули объектов существуют всегда**: у справочника/документа есть
  `Events/<Имя>EventHandler.*`, у проводимого документа — транзакционный скрипт.
  Пустые шаблоны — норма, их создаёт платформа; наполняй, не пересоздавай.
- **У подтипа документа — СКОЛЬКО УГОДНО транзакционных скриптов, не один**:
  переход в целевой подтип исполняет ВСЮ его цепочку скриптов по
  `executionOrder` (при равенстве — по времени создания), а не единственный
  скрипт-владелец. Дели по учётной цели — один скрипт на регистр (склад,
  себестоимость, обороты…), не один скрипт «на всё» — подробности и пример
  пары скриптов в `zuloone-new-document` §3.
- **Пользовательский переход подтипа — только команда.** После сохранения
  селект подтипа в карточке заморожен. Кнопка команды (скилл
  `zuloone-new-command`) проверяет условия и ставит целевой подтип — тогда
  и бегут проводки. Подтип со скриптами без команды перехода из UI не
  провести. Программный `SetSubtypeAsync` / `document.Subtype = …` — для
  сервисов, событий и тестов, не вместо кнопки.
- **`Menu/menu.json` — единственный авторитетный коллекционный файл**: пункт,
  удалённый из файла, УДАЛЯЕТСЯ из базы. Бесшаблонные пункты = «меню модели» —
  видны всем поверх любого шаблона интерфейса. Свой кусок меню можно прививать
  в чужую группу через `parentMetaId`.
- **Под корневой группой модели — подгруппы по виду объекта**: `Dictionaries`
  /«Справочники», `Documents`/«Документы», `Registers`/«Итоги»,
  `Reports`/«Отчёты» (`targetType: "Group"`, `parentMetaId` = корневая группа
  модели) — только те, что реально нужны. Риббон рисует ровно один уровень
  вложенности как колонки внутри вкладки модели; пункты объекта цепляй
  `parentMetaId`-ом к своей подгруппе по виду, не к корневой группе напрямую.
- **Зависимости между моделями** декларируются в `model.json` (dependencies,
  minVersion). Версия модели — semver в `model.json`: patch = фиксы кода,
  minor = аддитивные изменения, major = ломающие.
- **Повторяющиеся операции — в СЕРВИСЫ** (`zuloone-new-service`): логика,
  нужная больше чем одному скрипту (подбор, расчёт, генерация документов),
  живёт в сервисе и зовётся через `GetService<I<Имя>>()`. Тела событий,
  команд и проводок — ТОНКАЯ оркестровка: проверить, вызвать сервис,
  вернуть результат; копипаста между обработчиками — сигнал выносить.
- **Не хардкодить значения**: пороги, ставки, коды режимов — в глобальных
  константах (`GlobalConstants/<Имя>.json`, в коде типизированно
  `GlobalConstants.<Группа>.<Имя>` / `Get<T>` / `SetAsync`) или константах
  объекта; строки-подписи — в caption/переводах, не в коде.

## Скрипты — шаблоны классов (точные сигнатуры в `.generated/Frameworks/`)

| Что | Класс | База объявляется? |
|---|---|---|
| События справочника | `<Имя>EventHandler : TypedDictionaryEventHandler<Имя>` | да, сам |
| События документа | `<Имя>EventHandler : TypedDocumentEventHandler<Имя>` | да, сам |
| Транзакционный скрипт | `public partial class <ИмяTx>` + `override GetTransactions(<Документ> document, TransactionPairCollection, TransactionCollection)` | НЕТ — генерит платформа |
| Команда документа | `<Имя>Command : DocumentCommandBase<Документ>` + `override ExecuteAsync(<Документ> document, CommandContext context)` | НЕТ — генерит платформа |
| Драйвер итогов (хук) | `public partial class <Имя>TotalDriver` — переопределяет хуки расчёта | НЕТ — генерит платформа |
| Сервис | `public partial class <Имя>` — публичные методы образуют контракт `I<Имя>`, доступ из скриптов `GetService<I<Имя>>()` | НЕТ — plain class |
| Интеграционный тест | `class X : IntegrationTestScriptBase`, методы с `[IntegrationTest("…")]` | да, сам |

Проводки пишутся типизированно: `transactions.Add(new <Регистр> { <Измерение> =
…, <Ресурс> = дельта })`, двойная запись — `transactionPairs.Add(минус, плюс)`,
динамические аналитики — `RegisterMovementSpec("<Регистр>").Dim(...).An(...).Res(...)`.

**Корневые сервисы платформы доступны в ЛЮБОМ скрипте по умолчанию** —
`GetService<T>()` (в событиях/командах — `context.GetService<T>()`):
`IDocumentManager` (документы: загрузка/сохранение/связи),
`IDictionaryManager` и `IDictionaryManager<T>` (типизированные записи
справочников), `ILinkTableManager` (линк-таблицы: динамически по имени —
`Add/Ensure/Get/Delete`, и типизированно генерённым `LT_`-классом —
`GetRecordsAsync<T>(сторона, ключ)` / `SaveRecordAsync` /
`ReplaceRecordsAsync` — сторона становится ровно заданным набором),
`IDictionaryRecordManager`, `IDataService` (сырые записи любой таблицы),
`ISqlService` (запросы), `IRegisterMovementService` (движения регистров),
`IInformationRegisterService` (регистр сведений: Set / SliceLast / SliceFirst / Delete),
`IDocumentPostingService` (проведение/переходы), `IMetadataService`
(метаданные), `IConstantResolver` / `IGlobalConstantManager` (константы) —
плюс собственные сервисы моделей по контрактам `I<Имя>`.

## Обязательный цикл проверки

Ничего не считается сделанным без проверки (скилл `zuloone-verify`):

1. Синк применил файл: `docker logs zuloone-core-1 --since 2m | grep "Workspace sync"`
   (ищи `applied`, а не warning/error).
2. Компиляция: `POST http://localhost:5257/api/metadata/models/compile` — все
   модели `Ok`.
3. Схема: `POST http://localhost:5257/api/schema/sync` — физические таблицы.
4. Тесты: интеграционный тест в `Tests/` на каждый сценарий +
   `POST http://localhost:5257/api/metadata/tests/run-all`.

Если синк отклонил правку (Core-гейт, политика безопасности) — файл будет
переписан обратно значением из базы; не воюй с экспортом, ищи причину в логе.

## Документация и вики

При любом изменении, разработке нового кода или добавлении функциональности **обязательно**:

- **Обновить релевантную документацию** в wiki (d:\Sources\zulo.one\wiki\business\) — если
  изменилась архитектура, бизнес-логика, интеграции или API контракты;
- **Создать новую документацию**, если добавлена новая модель, сервис или сложная
  бизнес-процедура — опиши цель, основные сущности, ключевые сценарии, примеры
  использования сервисов (если это сервис);
- **Удалить или пометить устаревшей** документацию, если функциональность
  переработана, переименована или удалена — неактуальные доки сбивают с толку
  больше, чем полезны.

**Доки должны синхронны коду**, иначе они теряют смысл. Проверь:
- Имена объектов в доках совпадают с именами в коде
- Примеры скриптов отражают текущие сигнатуры и доступные сервисы
- Описание переходов состояний подтипов документа актуально
- Регистры и их аналитики описаны корректно
