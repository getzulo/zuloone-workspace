# Новый документ

## Модель состояний — сначала пойми это

**Подтип (subtype) — это ТЕКУЩЕЕ СОСТОЯНИЕ документа.** Документ живёт как
конечный автомат: `Черновик → Заказано → Оприходовано → …`. Переход между
подтипами — бизнес-событие:

- движок реверсит движения текущего состояния и исполняет транзакционную
  цепочку ЦЕЛЕВОГО подтипа — проводки всегда отражают текущее состояние;
- откат назад (в подтип без скриптов) просто снимает проводки;
- скрипты и события перехода могут менять связанную систему — в том числе
  ПОРОЖДАТЬ другие документы: заказ на покупку при переходе «Заказано →
  Оприходовано» создаёт документ прихода по заказанным строкам и проводит
  его, что порождает складские движения, и так далее по цепочке.

**Статусы (`statuses`) НЕ заводить.** Это легаси-механизм, дублирующий
подтипы, — он будет удалён из сущности документа. Состояние = подтип,
проведённость = `postOnSave: true` (сохранённый документ проведён в своём
текущем подтипе).

```json
      "subtypeCaption": "Оприходовано", "displayOrder": 3,
      "metaId": "<GUID-подтипа-Received>", "modelId": "<GUID модели>", "layerId": 1 }
  ],
  "tableParts": [
    { "documentTypeMetaId": "<GUID-документа>", "tablePartTypeMetaId": "<GUID-типа-строк>",
      "name": "Lines", "isCloneable": true,

```

- `ID`, номер и дата — системные, не объявляй.
- `displayOrder` подтипов = порядок workflow (движок различает переход
  вперёд/назад по нему). Первый подтип — начальное состояние; обычно без
  скриптов = черновик без движений.

## 3. Проводки состояния — `Documents/<Имя>/Transactions/*.*`

У подтипа может быть СКОЛЬКО УГОДНО транзакционных скриптов — по одному на
цель: складские движения, себестоимость, финансовые проводки, резервы…
При проведении состояния исполняется ВСЯ цепочка скриптов подтипа по
`executionOrder` (при равенстве — по времени создания); итог = объединение
движений всех скриптов. Дели по ответственности: один скрипт — один регистр
или одна учётная цель, так их можно менять и расширять независимо.

Каждый скрипт — своя пара файлов; `objectMetaId` = GUID ПОДТИПА:

```json
{
  "kind": "Script",
  "object": {
    "scriptType": "TransactionScript", "objectType": "Document",
    "objectMetaId": "<GUID подтипа>", "objectName": "<Имя документа>",
    "executionOrder": 1,
    "metaId": "<GUID-скрипта>", "name": "<Имя><Подтип><Цель>Tx",
    "modelId": "<GUID модели>", "layerId": 1
  }
}
```

`.cs` — БЕЗ объявления базового класса (framework генерится); имя класса
уникально во всём воркспейсе. Пример пары скриптов одного подтипа:
`ReceiptStockTx` (executionOrder 1 — складские остатки) и `ReceiptCostTx`
(executionOrder 2 — себестоимость):

```csharp
public partial class <Имя><Подтип><Цель>Tx
{
    protected override void GetTransactions(<Имя> document, TransactionPairCollection transactionPairs, TransactionCollection transactions)
    {
        foreach (var line in document.Lines)
        {
            transactions.Add(new <Регистр> { Warehouse = document.Warehouse, Item = line.Item ?? Guid.Empty, Quantity = line.Quantity ?? 0m });
            // двойная запись: transactionPairs.Add(минус, плюс);
            // динамическая аналитика: new RegisterMovementSpec("<Регистр>").Dim(...).An(...).Res(...)
        }
    }
}
```

`GetTransactions` — ЧИСТЫЙ расчёт движений, без побочных эффектов. Логика
перехода (создать связанный документ, дернуть сервис) — в событиях (шаг 4).

## 4. События перехода — `Events/<Имя>EventHandler.*`

База `TypedDocumentEventHandler<<Имя>>`. Ключевые хуки:

- `OnBeforePostAsync` — валидация перед проведением состояния;
  `EventResult.Cancel("причина")` блокирует переход;
- `OnAfterPostAsync` — состояние проведено: здесь порождаются связанные
  документы и прочие последствия перехода;
- `OnBeforeUnpostAsync` / `OnAfterUnpostAsync` — снятие движений при уходе
  из состояния.

**НЕ читай вторую таблицу в событии СОЗДАНИЯ** (`OnAfterSave` при `isNew`,
`OnAfterInsert`). Обращение к другой таблице в этой точке открывает новое
соединение внутри уже идущей транзакции вставки, что требует распределённой
транзакции — а её на Linux нет: падает вся вставка с
«This platform does not support distributed transactions», причём запись в логе
выглядит так, будто документ уже вставлен. Логику «при создании сходить в
справочник и что-то дописать» оформляй **командой документа** — она async и
выполняется вне этой транзакции (см. `zuloone-new-command`). В
`OnBeforePostAsync` на пути ПРОВЕДЕНИЯ чтения работают штатно — там открытых
соединений нет.

Порождение связанного документа (заказ → приход):

```csharp
public override async Task<EventResult> OnAfterPostAsync(PurchaseOrder header, EventContext context)
{
    if (header.Subtype != "Received") return EventResult.Ok();

    var docs = context.GetService<IDocumentManager>();
    var receipt = new GoodsReceipt { Warehouse = header.Warehouse };
    var order = await docs.GetDocumentAsync<PurchaseOrder>(header.MetaId);
    foreach (var line in order!.Lines)
        receipt.Lines.Add(new GoodsReceiptLinesTablePartRow { Item = line.Item, Quantity = line.Quantity });

    await docs.SaveDocumentAsync(receipt);              // postOnSave: приход проведётся сам
    await docs.AddLinkAsync(header.MetaId, receipt.MetaId); // родословная документов
    return EventResult.Ok();
}
```

В любом скрипте доступны СЕРВИСЫ — платформенные (`IDocumentManager`,
`IDictionaryManager`, `ILinkTableManager`, `IDataService`,
`IRegisterMovementService`, `IConstantResolver`, … — полный перечень в
CLAUDE.md) и свои (скилл `zuloone-new-service`):
`context.GetService<T>()` в событиях/командах, `GetService<T>()` — в любом
partial-скрипте.

**`OnAfterPostAsync` МОЖЕТ ВЫПОЛНИТЬСЯ ДВАЖДЫ — считай его повторяемым.**
Источников повтора ДВА, и путать их не надо:

1. *Перепроведение* — событие исполняется заново при КАЖДОМ проведении, а
   документы перепроводят буднично (правка накладной, откат и повтор). Это
   касается ЛЮБОГО документа.
2. *Двойное срабатывание за одно проведение* — если проведение само дописывает
   движения через менеджер (`ITotalsManager.PostMovementAsync` с тем же docId —
   так работает драйвер итогов, висящий на регистре), цепочка прогоняется
   второй раз. Это касается только документов, чьё проведение уменьшает
   покрытый драйвером ресурс: продажа со слоями себестоимости — да, приход —
   нет, он склад увеличивает.

Удваивается при этом НЕ всё — и разделительная черта простая:

- **Движения самого документа переживают повтор** — и проводки транзакционных
  скриптов, и то, что событие пишет менеджером под docId своего документа.
  Перепроведение их ЗАМЕНЯЕТ, а не добавляет. Поэтому склад, выручка, баллы и
  партия, заведённая выпуску производства, остаются верными.
- **Всё, что живёт ВНЕ документа, — удваивается**: порождённый связанный
  документ, проводка в GL, налоговый расчёт, вызов внешней системы. Их никто
  не заменяет, они просто появляются второй раз.

Ловится это плохо: удвоение видно только на данных, где вторичные движения
реально появляются. Тест, который заводит остаток прямым
`PostMovementAsync("Stock")`, драйвер себестоимости не запускает — и проходит
зелёным, пока в проме каждая продажа товара со слоями удваивает и разноску в
книге, и налоговый расчёт (то есть выходной НДС в декларации). Ровно так оба
бага и прожили незамеченными; поймал их тест, отличавшийся от зелёного соседа
ровно одной строкой — партией себестоимости у товара. **Если пишешь тест на
побочный эффект проведения — заводи остаток ПРИХОДОМ, а не движением
регистра.**

Поэтому побочный эффект в `OnAfterPost` делай ИДЕМПОТЕНТНЫМ, и лучше — в
сервисе, который его исполняет, чтобы защиту получили все вызывающие сразу:

```csharp
// GeneralLedgerService.PostAsync: описание несёт id документа-источника и
// назначение ("Sales invoice <id>"), поэтому повтор = тот же факт, а не второй.
if (await _documents.CountDocumentsAsync<JournalEntry>(
        $"Description = '{description.Replace("'", "''")}'") > 0)
    return null;
```

Ключ идемпотентности бери из источника (id или номер документа + назначение), а
не из времени или счётчика. Проверка «уже сделано» обязана переживать и отмену с
перепроведением: первую проводку никто не сторнировал.

**Порождение НЕОБЯЗАТЕЛЬНОГО контура — только мягко.** Если событие включает
побочный контур (налоговый расчёт, разноска в GL, начисление баллов), которого
у большинства стендов ещё нет, оно обязано БЕЗ ШУМА ничего не делать, когда
контур не настроен: нет кода налога по умолчанию — счёт выставляется как
раньше. Иначе включение фичи ломает все существующие документы. Настройку
читай из singleton-справочника настроек модуля, а не из константы в коде, и
пиши ДВА теста: «контур настроен → документ порождён» и «контур не настроен →
документ проводится как раньше, ничего не порождено».

**НОВОЕ ОГРАНИЧЕНИЕ на существующее поведение — через флаг настроек, и флаг по
умолчанию РАЗРЕШАЮЩИЙ.** Это отдельное правило от предыдущего: там речь про
добавление контура, здесь — про запрет того, что раньше было можно. Заводить
поле «нельзя» в `<Модуль>Settings` (`EnforceWarehouseTasks`), а не включать
проверку безусловно, потому что документы и тесты уже написаны под старую
свободу: жёсткое включение дисциплины ячеек уронило бы около тридцати тестов,
часть которых вообще указывает несуществующие ячейки.

Флаг называй так, чтобы РАБОЧИМ было `false` (необязательный `Boolean` генерится
не-nullable), и **обязательно покрой тестом ВЫКЛЮЧЕННОЕ состояние** — сценарий
«флаг снят, всё как раньше» и есть страховка существующих документов; он важнее
сценария с включённым флагом.

И раздели, что именно флаг выключает. ФИЗИКУ он выключать не имеет права:
«нельзя переставить больше, чем лежит в ячейке» действует всегда, а
«приёмка это приёмка» — политика, ей флаг и управляет. В одном обработчике это
две разные проверки, и смешивать их в одно условие нельзя.

Обёртка `try/catch` вокруг такого блока уместна — но помни цену: **проглоченное
исключение делает отказ немым**, в тесте будет виден только нулевой результат
(«дебет 0»), без причины. Поэтому логируй пойманное и держи тест, который бьёт
именно по эффекту контура, а не по факту сохранения документа.

**Тела событий держи тонкими.** Повторяющиеся операции (как генерация
прихода выше, если она нужна ещё где-то) оборачиваются в сервис — событие
только решает КОГДА, сервис знает КАК. Пороги и коды режимов не хардкодятся —
глобальные константы (`GlobalConstants.<Группа>.<Имя>`) или константы
документа; правишь значение — код не трогаешь.

## 4а. Защита от дурака: что подтип умеет запрещать

Два флага на подтипе, оба объявляются прямо в `subtypes` и едут с моделью через
воркспейс и бандлы. Оба — «оборона в глубину»: проверка стоит на сервере, UI
только не предлагает того, что всё равно будет отклонено.

**`isReadOnly: true` — данные документа заморожены.** Пока документ в этом
подтипе, отклоняются правки И строк табличных частей, И полей шапки — на любом
пути: из UI, из скрипта, из интеграции. Ставь на КОНЕЧНЫЕ состояния: проведённая
проводка, оплаченный счёт, выпущенный заказ. Перевод в другой подтип при этом
остаётся возможен — иначе из состояния не было бы выхода.

**Следствие для КОДА, который порождает документы:** нельзя создать документ
СРАЗУ в запертом подтипе — строки пишутся уже после того, как шапка получила
подтип, и гард их отклонит («Документ в подтипе «X» доступен только для
чтения»). Порядок всегда такой: сохранить в исходном подтипе со строками, затем
перевести отдельным шагом.

```csharp
var doc = await _documents.NewDocumentAsync<Начисление>("Draft", header);
foreach (var r in rows) doc.Lines.Add(r);
await _documents.SaveDocumentAsync(doc);                       // строки — пока открыт
await _posting.SetSubtypeAsync(ТипДокумента, doc.MetaId, "Posted");   // и только потом запереть
```

То же в тестах: `CreateDocumentAsync(..., subtype: "Posted")` в запертый подтип
не пройдёт — создавай и вызывай `ChangeSubtypeAsync` отдельно.

**Карта переходов** — какие подтипы могут следовать за данным. Пустой набор
означает **«разрешено всё»**, поэтому модели без карты работают как раньше;
объявляй маршруты только там, где перепрыгивание этапа — ошибка:

```json
"subtypeTransitions": [
  { "fromSubtypeMetaId": "<GUID Draft>", "toSubtypeMetaId": "<GUID Ordered>",
    "name": "Draft->Ordered", "metaId": "<НОВЫЙ GUID>",
    "modelId": "<GUID модели>", "layerId": 1 }
]
```

Обратный ход оставляй свободным: откат из проведённого состояния — штатная
операция (движок сам снимает движения), и запирать его значит лишить возможности
исправить ошибку. Ограничивай только движение «вперёд».

В дизайнере то же самое: вкладка «Subtypes» — галка «Данные только для чтения» и
мультиселект «Разрешённые переходы».

## 4б. Проставить поле шапки «при переходе в состояние X»

Типовая задача: при выставлении счёта записать в шапку то, что вычисляется
(юрлицо продавца, скидка уровня лояльности, курс) — и чтобы проводки это
УВИДЕЛИ. Место, где это работает, ровно одно, и найти его с первого раза
мешают три ловушки.

**Ловушка 1: `OnBeforePost` в базу не пишет.** У пост-событий нет WriteBack:
экземпляр, приехавший в событие, до базы не доезжает — присваивание
`header.Поле = …` живёт только внутри метода. Точечный `UpdateDocumentAsync`
оттуда в базу попадает, но проводки его не увидят (ловушка 2). В итоге поле
применится только там, где документ ПЕРЕЧИТЫВАЕТСЯ (`OnAfterPost`), а проводки
посчитают по-старому — леджер разъедется, и разъедется молча.

**Ловушка 2: проводки читают СНИМОК шапки.** Движок читает шапку из базы один
раз, до начала проведения, и кормит этим словарём всю цепочку транзакционных
скриптов. Записанное в базу ПОСЛЕ этого чтения для проводок не существует.

**Ловушка 3: `SaveDocumentAsync` не пишет `Subtype`.** Подтип — поле платформы
(как `ID`, `Number`, `StatusValue`): его меняет отдельный движок, точечным
`UPDATE` одной колонки. Поэтому в `OnBeforeSave`, вызванном сохранением
документа, `header.Subtype` — СТАРЫЙ (или null), и проверка «если Issued» там
не сработает никогда.

Рабочая точка — before-событие того самого точечного `UPDATE` подтипа: оно
случается ПЕРЕД сбором проводок, а WriteBack на update работает, так что
значение уезжает в тот же `UPDATE`.

```csharp
public override async Task<EventResult> OnBeforeSaveAsync(SalesInvoice header, bool isNew, EventContext context)
{
    if (isNew || header.Subtype != "Issued" || header.MetaId == Guid.Empty) return EventResult.Ok();

    // В событие ЧАСТИЧНОГО обновления приходят ТОЛЬКО пишущиеся колонки — здесь
    // это один Subtype, а Customer и текущее значение поля в экземпляре нули.
    // Судить по нему о документе нельзя, документ перечитывается.
    var stored = await context.GetService<IDocumentManager>().GetDocumentAsync<SalesInvoice>(header.MetaId);
    if (stored == null || stored.Customer == Guid.Empty) return EventResult.Ok();
    if (stored.DiscountPercent > 0m) return EventResult.Ok();   // введено руками — не трогаем

    header.DiscountPercent = await CalculateAsync(stored, context);   // WriteBack → тот же UPDATE
    return EventResult.Ok();
}
```

Три правила отсюда, годные и вне этой задачи:

- **`header` в событии обновления — это ПЕЙЛОАД, а не запись.** Читай из него
  только то, что заведомо пишется; остальное — перечитыванием. `MetaId`
  платформа в пейлоад кладёт, на него опираться можно.
- **Заполненное руками не переписывай.** Вычисленное значение ставится только
  поверх пустого: юрлицо и скидка, введённые человеком, — его решение.
- **Тест обязан проверять СУММЫ, а не только поле.** Утверждение
  «`stored.Поле == 10`» зеленеет и тогда, когда проводки поле не увидели.
  Проверяй все денежные ноги разом — дебиторку, выручку, налог, баллы: они
  обязаны сойтись от ОДНОЙ базы, и именно это ломается при ошибке в точке
  штамповки.

## 4в. Дата побочного эффекта — ДАТА ДОКУМЕНТА, не `UtcNow`

`OnAfterPost` выполняется в момент нажатия «Провести», поэтому взять там
`DateTime.UtcNow.Date` кажется естественным. Для всего, что уходит в учёт
(проводка в главную книгу, порождённый документ, движение регистра), это
ОШИБКА, и видно её только на документах, проводимых задним числом.

Дата выбирает УЧЁТНЫЙ ПЕРИОД. Регистры двигаются датой документа, а проводка
с `UtcNow` уходит в период дня разноски: августовская накладная, проведённая
второго сентября, кладёт подсистему в август, а книгу в сентябрь. Сверка за
период расходится на сумму всех опоздавших документов, и закрытый август уже
не исправить.

```csharp
// Дату бери с ПЕРЕЧИТАННОГО документа — он тут и так нужен ради строк.
var inv = await context.GetService<IDocumentManager>().GetDocumentAsync<SalesInvoice>(header.MetaId);
await gl.PostAsync(inv.DocumentDate, ...);
```

Если разносит общий сервис — параметр `DateTime date` у него ОБЯЗАТЕЛЬНЫЙ, без
значения по умолчанию: подстановка «сегодня» по умолчанию и есть тот самый баг.

Тест на это пишется так: два НЕПЕРЕСЕКАЮЩИХСЯ учётных периода (прошлый и
текущий), документ датируется прошлым — проверяются и дата проводки, и
выбранный период (одной даты мало: период выбирается по ней отдельным шагом).
Образец — `GLIntegration/Tests/PostingDateGLTest.cs`.

## 5. Переход состояния снаружи

UI двигает подтип в форме документа; программно — `SaveDocumentAsync` с
изменённым `Subtype` (движок сам реверсит и пересеивает) или API
`POST /api/documents/{typeId}/{docId}/subtype`.

Это НЕОХРАНЯЕМЫЙ переход — годится для системных/событийных переводов, где
условия уже проверены выше по цепочке. Если переход должен явно проверять
готовность (есть строки, хватает остатка…) и давать пользователю кнопку —
это **команда**, см. скилл `zuloone-new-command`.

## 6. Меню + проверка

Пункт `targetType: "Document"` в `Menu/menu.json`, `parentMetaId` — GUID
подгруппы **`Documents`/«Документы»** модели (`zuloone-new-model`), не
корневой группы напрямую. Затем `zuloone-verify` + интеграционный тест на
ПЕРЕХОДЫ: создать → перевести по состояниям → остатки регистров сходятся на
каждом шаге, включая откат назад.
