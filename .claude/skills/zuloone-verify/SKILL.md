# Проверка изменений

Правка файла воркспейса «сделана» только когда прошла все четыре ступени
**и** у каждой затронутой модели поднят `modelVersion` в её `model.json`.
Тенант заливает модель только если версия отличается от уже установленной;
тот же номер — заливки не будет.
Сервер dev-стенда: `http://localhost:5257` (ядро в docker: контейнер
`zuloone-core-1`).

## 0. Если в логе синка ПУСТО — сначала проверь предохранитель

Синк умеет вставать на стоп целиком. Когда файлов, разошедшихся с последним
экспортом, набирается больше порога, он ПЕРЕСТАЁТ применять что-либо — включая
твои новые файлы, — чтобы не затереть чужую работу:

```bash
curl -s http://localhost:5257/api/dev/workspace/sync-status
# {"held":true,"reason":"551 file(s) edited outside the exporter","quarantined":[...]}
```

Симптом обманчив: файл сохранён, лог молчит, объект в базе не появляется, и
кажется, что «синк отвалился». На деле он жив и намеренно бездействует.

Снятие — `POST /api/dev/workspace/sync-resume`, и вот чего нельзя не знать:

- **`sync-resume` не «принимает» файлы, а ОТБРАСЫВАЕТ их** (`discarded: 551`):
  истиной объявляется база, и диск переписывается из неё. Всё, что ты написал в
  `.cs`, пока гейт был закрыт, ИСЧЕЗНЕТ — json новых объектов уцелеет только
  потому, что в базе их нет и переписывать нечем.
- Хочешь наоборот, диск → база: сначала `POST /api/dev/workspace/import-all`.
  Он НЕ снимает гейт (после него `held` всё ещё `true`) — resume нужен отдельно,
  и он снова отбросит расхождения.
- **Порядок, который работает**: снять гейт → и ТОЛЬКО ПОТОМ писать файлы.
  Если файлы уже написаны — сверь их после resume и перепиши заново.
- **На стенде с двумя инстанциями (5257 SQL Server и 5258 Postgres) папка
  воркспейса ОДНА, а базы разные.** `sync-resume` на второй перепишет диск из
  ЕЁ базы — то есть откатит то, что только что принял первый. На второй
  инстанции гейт не трогай: заливай точечно через `apply-file` (см. ниже).

**Гейт бывает ЧУЖОЙ — тогда его не снимают, а ждут.** Держаться он может
часами и не из-за тебя: 2026-09-22 он стоял с 01:46 на 84 файлах чужой
незакоммиченной волны, и правка двух подписей в `Menu/menu.json` шесть часов
не доезжала до базы. Симптом тот же, но добавляется ещё один обман: **API
продолжает отвечать СТАРЫМ значением**, без ошибки — то есть проверка
«прочитал объект через его же API» подтверждает не твою правку, а прошлое
состояние. Держится гейт на весь воркспейс, а не только на карантинные пути.

Поэтому:

- `sync-status` — ПЕРВОЕ, что делаешь, а не то, к чему приходишь после трёх
  кругов диагностики. Одна команда вместо grep'а по логу: во время `run-all`
  твои строки утонут в `Data import applied` от сидов тестов. Если всё-таки
  ищешь в логе — шаблон называется `Workspace sync HELD`, в записи есть
  `Count` и список `Files`.
- Если в карантине чужие файлы — **не снимай**: `import-all` затащит на общий
  стенд чужую незаконченную работу, `sync-resume` её отбросит. Правку оставь
  в файле, скажи владельцу волны и НЕ объявляй изменение проверенным: оно
  в базе не побывало.

## 1. Синк применил файл (~2–4 с после сохранения)

```bash
docker logs zuloone-core-1 --since 2m 2>&1 | grep "Workspace sync"
```

- `<файл> applied (N created, M updated…)` — применилось.
- `Workspace sync: <warning>` — что-то проигнорировано (сирота без envelope,
  Core-гейт, неизвестный вид) — разберись, прежде чем идти дальше.
- Ничего не появилось — файл не входит в отслеживаемые (`.json`/`.cs`/`.vt`)
  или лежит в игнорируемой папке.
- Если правку ОТКЛОНИЛИ (Core, политика безопасности) — экспорт перепишет файл
  обратно; `git diff` покажет откат.
- **Правка может потеряться и БЕЗ отказа** — гонка с экспортом. Сервер
  периодически выгружает всю базу в файлы (`Workspace export: … N written`);
  запись, попавшая в этот момент, будет затёрта версией из базы, и в логе не
  появится СТРОКИ `applied` для твоего файла — только тишина. Поэтому после
  правки `.cs`/`.json` **убеждайся, что она на диске** (`grep` по добавленному
  имени) и что в логе есть `<файл> applied`. Нет ни того, ни другого — просто
  запиши файл ещё раз, экспорт не воюет, он всего лишь опередил.

## 2. Компиляция моделей

```bash
curl -s -X POST http://localhost:5257/api/metadata/models/compile
```

Каждая модель должна быть `"status":"Ok"`. `Failed` несёт первую ошибку
компилятора с именем скрипта; `DependencyFailed` — сломана зависимость.
Типовые причины: опечатка в имени свойства сущности (сверься с
`.generated/Entities/<Имя>.cs`), дубль имени класса в модели, объявленная база
у partial-скрипта, которому её генерит платформа.

## 3. Схема БД

Новые объекты/поля требуют физических таблиц:

```bash
curl -s -X POST http://localhost:5257/api/schema/sync
```

Посмотреть, что будет сделано, не делая: `GET /api/schema/detect`.

**`"Schema synchronized successfully"` — это не «таблица создана».** Ответ
значит ровно «синк не бросил исключение», а не сделать ничего — это тоже не
бросить исключение. Если объект новый, доказательство — `detect` ПОСЛЕ синка:
очередь должна быть пуста. Расхождение «синк зелёный, а обращение к таблице
даёт `relation … does not exist` / `Invalid object name`» означает, что синк
считает таблицу уже существующей: ищи в базе объект-двойник с тем же именем в
другом регистре или в другой схеме.

## 4. Интеграционные тесты

На каждый бизнес-сценарий — тест в `Tests/` своей модели (пара `Имя.json` +
`Имя.cs`):

```csharp
using ZuloOne.Runtime.Testing;

public class <Имя>Test : IntegrationTestScriptBase
{
    [IntegrationTest("<Что проверяем>")]
    public async Task Scenario()
    {
        var wh = Db.NewId();
        // создать запись/документ, провести, проверить остатки
        await Db.PostMovementAsync("<Регистр>", DateTime.UtcNow.Date,
            new Dictionary<string, object?> { ["Warehouse"] = wh },
            new Dictionary<string, decimal> { ["Quantity"] = 7m });
        Assert.IsTrue(/* … */, "сообщение с {0}", значение);
    }
}
```

Запуск:

```bash
curl -s -X POST http://localhost:5257/api/metadata/tests/run-all      # все
curl -s -X POST http://localhost:5257/api/metadata/tests/<GUID>/run   # один
```

## СНАЧАЛА БАЗОВАЯ ЛИНИЯ, ПОТОМ ВИНА

Прогоняй затронутые наборы ДО своей правки и записывай числа. Красный тест
после правки — ещё не твой красный тест: стенд общий, и рядом идёт чужая работа.

Это стоило целой сессии. Добавление поля в шапку `PurchaseOrder` совпало с
падением `SubtypeGuardsTest.LockedSubtypeStillAllowsTransitionOut`, и совпадение
выглядело причинно: поле новое, колонка у старых строк NULL, а
`SaveDocumentAsync` сужает запись до колонок, которые ДОКАЗУЕМО равны хранимым
(`kv.Value.Equals(stored)`), и `Guid.Empty.Equals(null)` — ложь. Значит колонка
всегда в записи, запись перестаёт быть «только переход» (`Subtype`/`StatusValue`),
и выход из запертого подтипа отклоняется. Механизм подтверждался кодом
платформы, объяснял симптом целиком — и был НЕ ПРИ ЧЁМ: после удаления поля из
файла, из базы и рестарта ядра тест падал ровно так же. Он падал и до начала
работы.

Проверка стоит одного прогона:

```bash
# ДО первой правки
curl -s -X POST http://localhost:5257/api/metadata/tests/<GUID>/run   # 5/6 — запомнить
```

Правдоподобный механизм, выведенный из исходников, — это ГИПОТЕЗА, а не
доказательство. Доказательство — только измерение с правкой и без неё.

## Когда «ничего не менял, а всё красное»

Стенд общий, и три причины дают лавину падений, не связанных с твоей правкой.
Проверяй их ДО того, как чинить свой код.

**1. Мусор от чужого прогона.** Имена в ошибках с восьмизначным хвостом —
`TR_PosStock_918e5a83`, `Invalid object name 'TR_Freedb94a15b'` — значит рядом
идёт прогон xunit-набора: он создаёт и удаляет метаданные прямо между твоими
тестами. Осиротевший скрипт при этом валит компиляцию `Core`, а за ней **все**
модели (`Dependency failed`). Лечится метлой:

```bash
curl -s "http://localhost:5257/api/dev/test-artifacts/orphans"          # посмотреть
curl -s -X POST "http://localhost:5257/api/dev/test-artifacts/sweep" -H "Content-Type: application/json" -d '{}'
```

Если чужой прогон ещё идёт — мерить бессмысленно, числа будут скакать между
запусками без единой твоей правки. Дождись тишины.

**2. Синк стоит.** `Workspace sync: cannot activate ...` в логе означает, что
путь воркспейса указывает не туда, и **ни одна правка файлов не доезжает до
базы** — молча. Проверить и вернуть:

```bash
curl -s http://localhost:5257/api/dev/workspace/settings
curl -s -X PUT http://localhost:5257/api/dev/workspace/settings -H "Content-Type: application/json" -d '{"path":"/workspace"}'
```

**3. Задвоенные модели.** Две модели с одинаковым именем — почти всегда след
пересева с `force`. Удалять дубликат ОПАСНО: снос модели дропает физические
таблицы по ИМЕНАМ, не проверяя, не пользуется ли ими вторая модель с теми же
объектами. Если всё же удалил — сразу `POST /api/schema/sync`, он пересоздаст
таблицы из уцелевших метаданных.

## Быстрая диагностика

| Симптом | Куда смотреть |
|---|---|
| Файл «не применяется» | шаг 1: лог синка; envelope рядом с .cs есть? kind верный? |
| CS0246 «тип не найден» | объект ещё не создан/не скомпилирован — шаги 1–2 по порядку |
| 500 при записи данных | `docker logs zuloone-core-1 --since 5m` — реальный стек |
| Проведение без движений | скрипт привязан не к тому подтипу (`objectMetaId`) |
| Правка «откатилась» | Core-гейт или политика безопасности — шаг 1, лог |
| Правка исчезла, в логе про неё НИЧЕГО | гонка с экспортом — записать файл заново, проверить `applied` |
| Объект «применился», но сущности в `.generated/` нет | ссылка на объект, которого в тот момент не было (документ → тип строк, `Service` → свой скрипт). В логе рядом — `INSERT … conflicted with the FOREIGN KEY`. Лечится ПОВТОРНОЙ записью того же файла, когда зависимость уже в базе |
| Компиляция отдаёт 500 без тела | смотри `docker logs`: длинная ошибка не влезла в колонку статуса. Настоящую диагностику по сервисам даёт `POST /api/services/rebuild` |
| Сервис изменён, а потребитель не видит метод | сначала должен примениться файл СЕРВИСА, потом компиляция; `CS1061 I<Сервис> не содержит` = контракт собран со старого кода |
| Тесты массово падают `InvalidOperationException: Service I<Х> is not available` — причём в РАЗНЫХ, не связанных друг с другом сервисах (свой + чужие) | **Тексту не верь, он врёт про причину.** Это РАССИНХРОН ПОКОЛЕНИЙ КОНТРАКТОВ: `ScriptServiceResolver` сервис НАХОДИТ, но отбраковывает на `IsInstanceOfType` и пишет настоящую причину в лог уровнем Error — `docker logs zuloone-core-1 \| grep "different generation"` → `Requested: …Contracts.Inventory.v83 vs Provided: Service_…`. Каждая пересборка реестра выпускает НОВУЮ сборку контрактов (за час живой правки наблюдалось `v83 → v187`), а уже загруженные обработчики событий держат интерфейсы прежнего поколения. Лечит `POST /api/metadata/models/compile` — он последним шагом зовёт `LoadAllEventHandlersAsync`. **`POST /api/services/rebuild` эту поломку СОЗДАЁТ**: контракты бампает, обработчики не перезагружает (починено 2026-09-21, нужна пересборка образа). Следствие: на стенде, который правят прямо сейчас, `run-all` зелёным не будет в принципе — гоняй сразу после `models/compile`, без сохранений между |
| В логе синка ПУСТО, объект не появляется | шаг 0: гейт (`sync-status`) — не «отвалился», а намеренно стоит |
| `models/compile`: Core `Failed`, все модели `DependencyFailed`, причина не названа | сломана ЕДИНАЯ сборка контрактов — почти всегда свой тип в публичной сигнатуре сервиса (`zuloone-new-service` §2в). Виновника называет только `POST /api/services/rebuild` |
| Новый ДОКУМЕНТ применился, а скрипт его не видит (`CS0246 <Документ>`) | сущности документа генерятся не на лету: `schema/sync` + `models/compile` НЕ помогают, нужен `docker restart zuloone-core-1` (потом компиляция снова зелёная) |
| Новый СПРАВОЧНИК/ПОЛЕ применились, а сборка контрактов их не видит (`Core Failed: Service contracts do not compile: CS0246 <Справочник>`, всё остальное `DependencyFailed`) | то же самое и то же лечение — `docker restart`. Отличать от «своего типа в публичной сигнатуре» (там `POST /api/services/rebuild` называет виновника): здесь виновник УЖЕ назван в тексте, и это имя только что заведённого объекта. Всплывает, как только публичный метод сервиса принимает или возвращает новую генерённую сущность |
| Аналитика регистра «не привязана» при `PostMovementAsync` | имя аналитики ≠ имя поля: ошибка перечисляет привязанные (`Bound: TaxCode, TaxDirection, LegalEntity`) — бери имя оттуда, и то же имя читай в `ExpandAsync` |
| `schema/sync` отдаёт `Base type '<X>' is not in the catalog` | опечатка в `baseType`: целое — `Integer`, не `Int`. Импорт такое поле принимает молча, спотыкается только схема — объект в базе есть, таблицы под него нет |
| `run-all`: падают только `Tb*`-классы с `SqlException: Execution Timeout Expired`, все ровно на ~31 с | НЕ твоя правка и не наводка от параллельного прогона (воспроизводится поодиночке). Это платформенные тесты TestBench, создающие МЕТАДАННЫЕ: харнес держит собственную незакоммиченную транзакцию (сессия `sleeping`, `open_transaction_count=1`), а чтение метаданных идёт другим соединением и висит на `LCK_M_S` по `MetaNumberSequences` до таймаута команды. Проверяется семплированием `sys.dm_exec_requests` во время прогона: в покое открытых транзакций НЕТ, блокировщик появляется только на время теста. Бизнес-слоя не касается — чинить в репозитории платформы |

## Точечная заливка файла, когда синк молчит или трогать его нельзя

```bash
curl -s -X POST http://localhost:5257/api/dev/workspace/apply-file \
  -H "Content-Type: application/json" \
  -d '{"file":"Tax/Documents/TaxReturn/TaxReturn.object.json","force":true}'
# {"created":11,"updated":18,"unchanged":0,"coreRejected":0,"errors":[]}
```

Читай ответ, а не факт 200: `unchanged: 1` означает, что база УЖЕ содержит этот
текст (полезно, чтобы отличить «правка не доехала» от «доехала, а сломано
другое»). Диск этот вызов не трогает — поэтому им безопасно заливать вторую
инстанцию.

**`created=0 updated=0 errors=[]` — НЕ обязательно «всё уже применено».**
Ровно то же самое возвращается, когда сервер вообще не смог ПРОЧИТАТЬ файлы:
путь воркспейса в базе указывает не туда. Проверь
`GET /api/workspace/settings` (`{path, dbValue, configValue, source}`) и сравни
с бинд-монтированием контейнера (`docker inspect zuloone-core-1` → секция
`Mounts`): если хост-папка смонтирована в `/workspace`, то и в настройке обязано
стоять `/workspace`.

В логе это видно как `Workspace sync: cannot activate /app/C:\workspace` —
виндовый путь внутри Linux-контейнера. `PUT /api/workspace/settings` такие пути
отвергает, так что попасть туда значение могло только в обход.

**Поэтому проверяй результат ЧЕРЕЗ САМ ОБЪЕКТ, а не по ответу заливки:**
`GET /api/metadata/tests/{id}` и поиск своей строки в `code`. А если код нужен в
базе прямо сейчас, а синк не поднять — заливай напрямую:
`PUT /api/metadata/tests/{id}` с полной записью (name, description, code,
targetObjectType, targetObjectMetaId, isActive, groupName). Синк для этого не
нужен вовсе.

**Предохранитель по размеру:** больше 25 изменённых файлов в одном вызове
`apply-files` отклоняются целиком («wholesale file-side rewrite, not a live
edit»). Дроби пакет и НЕ клади в список удалённые файлы.

**Это же — способ проверить СВОЮ правку под ЧУЖИМ гейтом, не снимая его.**
2026-09-22 гейт стоял шесть часов на 84 файлах чужой волны, и правка подписей
в `Inventory/Menu/menu.json` всё это время не доезжала до базы. Снимать нельзя
(см. §0), ждать — значит объявить изменение проверенным по факту «файл на
диске лежит». Выход: `apply-file` на ОДИН свой файл. Диска он не трогает,
чужой карантин не разбирает, радиус — ровно твой объект:

```bash
curl -s -X POST http://localhost:5257/api/dev/workspace/apply-file \
  -H "Content-Type: application/json" \
  -d '{"file":"Inventory/Menu/menu.json","force":true}'
# {"created":0,"updated":4,"unchanged":21,"errors":[],"warnings":[]}
```

Дальше — обязательно чтение через API самого объекта (`GET
/api/metadata/menu`), потому что `updated: 4` говорит «база приняла», а не
«видно то, что задумано». И честно скажи, какой слой проверен: правка подписей
компиляцию и схему не затрагивает, гонять `run-all` на общем стенде ради неё —
только мешать соседу.

Порядок важен: объект, ссылающийся на другой (сервис → свой скрипт, документ →
тип строк), при первом проходе даст `violates foreign key` — повтори тот же
файл после того, как зависимость применилась.

**Заливай `.json`, а не `.cs`.** Код едет прицепом к своему envelope: правка
`X.cs` доедет до базы только вместе с `X.script.json` (у теста — с `X.json`).
Пока гейт держит синк, отредактированный `.cs` сам по себе не значит НИЧЕГО —
сервер продолжает компилировать старый текст, прогон показывает прежнее
поведение, и ты идёшь искать несуществующую ошибку в логике. Признак ровно
этот: правишь код, а падение не меняется ни на символ.

**Пакеты данных `apply-file` НЕ ставит** — они не envelope, и ответ это честно
говорит в `warnings`: `not a workspace envelope: …/DataPackages/vat-UA.json`
(при `created=0 updated=0 errors=[]`, то есть по ответу «успех»). Ставятся своим
маршрутом:

```bash
curl -s http://localhost:5257/api/data-packages          # id, и applied: true/false
curl -s -X POST http://localhost:5257/api/data-packages/apply \
  -H "Content-Type: application/json" -d '{"id":"LocalizationUkraine/vat-UA"}'
# {"ok":true,"inserted":7,"updated":0,"skipped":13,"errors":0,"issues":[]}
```

`apply` — это upsert по бизнес-ключу: дописать строки в существующий пакет
безопасно. **`recreate` УДАЛЯЕТ все строки таблиц пакета** и сеет заново — на
общем стенде это сносит чужие данные в тех же таблицах (`TaxCode`, `Tax`…). Не
путай их.

Не забудь `rowCount` в манифесте: он обязан совпасть с длиной массива в `data`.

Полный прогон платформенного бенча (если стенд разработческий):
`POST /api/dev/totals-testbench` — не обязан быть зелёным из-за твоих правок
бизнес-моделей, но не должен ЛОМАТЬСЯ ими.
