# Новый сервис

Сервис — класс с перечнем методов, выполняющих ту или иную функцию
(`LocationService`: поиск страны по городу, города по координатам). Из его
ПУБЛИЧНЫХ методов платформа генерит контракт-интерфейс `I<Имя>`, и сервис
доступен из ЛЮБОГО скрипта системы через `GetService<I<Имя>>()`.

Одно имя контракта `IFoo` на нескольких слоях — Chain of Command: верхний
стартует первым, `next<T>(...)` идёт вниз (скилл `zuloone-extend` §2б).
Проглотить нижний — `[Replace]`. Нужно другое поведение, не обёртка — другое
имя контракта.

ПРАВИЛО, не рекомендация: повторяющаяся операция оборачивается в сервис.
Логика нужна больше чем одному скрипту, или это самостоятельная бизнес-функция
(подбор, расчёт, генерация связанных документов) — она живёт здесь. Событиям,
командам и проводкам остаётся тонкая оркестровка: проверить условие, вызвать
сервис, вернуть результат. Заметил копипасту между обработчиками — выноси.
Магические числа и коды режимов сервису тоже не принадлежат — глобальные
константы (`GlobalConstants.<Группа>.<Имя>`).

## 1. Файлы — `Services/<Имя>/`

`<Имя>.json` — регистрация сервиса:
```json
{
  "kind": "Service",
  "object": {
    "description": "<Что делает сервис>",
    "namespace": "ZuloOne.Services",
    "scriptMetaId": "<GUID-скрипта>",
    "metaId": "<GUID-сервиса>", "name": "<Имя>",
    "modelId": "<GUID модели>" }
}
```

`<Имя>Service.script.json` — envelope кода:
```json
{
  "kind": "Script",
  "object": {
    "scriptType": "Service", "objectType": "Service", "objectName": "<Имя>",
    "metaId": "<GUID-скрипта>", "name": "<Имя>Service",
    "modelId": "<GUID модели>" }
}
```

`<Имя>Service.cs` — сам класс. **Имя класса РАВНО имени сервиса** (не имени
скрипта!) — из него генерится контракт `I<Имя>`:

```csharp
// Сервис "LocationService": публичные методы образуют контракт ILocationService.
public partial class LocationService
{
    // Платформенные сервисы — через конструктор (DI).
    private readonly IDataService _data;
    public LocationService(IDataService data) => _data = data;

    /// <summary>Страна по городу (ID записи City → ID записи Country).</summary>
    public async Task<Guid?> FindCountryByCityAsync(Guid cityId)
    {
        var city = await _data.GetByIdAsync("City", cityId);
        return city?["Country"] as Guid?;
    }

    /// <summary>Ближайший город по координатам.</summary>
    public Task<Guid?> FindCityByCoordinatesAsync(decimal lat, decimal lon)
    {
        // …
        return Task.FromResult<Guid?>(null);
    }
}
```

Правила класса:
- публичный метод = метод контракта; приватное/внутреннее в контракт не попадает;
- зависимости — только платформенные сервисы через конструктор;
- без состояния между вызовами (сервис — функции, не хранилище);
- никаких опасных API (файлы, сеть, процессы) — политика безопасности отклонит.

## 2. Использование — из любого скрипта

```csharp
// в транзакционном скрипте, драйвере, тесте — статический хелпер:
var location = GetService<ILocationService>();

// в обработчике событий или команде — через контекст:
var location = context.GetService<ILocationService>();

var country = await location.FindCountryByCityAsync(cityId);
```

`TryGetService<T>()` возвращает null вместо исключения, если сервис не
зарегистрирован (опциональная зависимость).

Сервис из ДРУГОЙ модели — объявить зависимость в `model.json`
(скилл `zuloone-new-model`).

## 2. CoC — обернуть чужой `I<Имя>`

Тот же `name` в своей модели (слой строго выше) — луковица, не замена:
`GetService<IFoo>()` стартует с тебя, `next<T>(те же аргументы)` зовёт владельца.
Асинхронно — `await nextAsync<T>(...)`. Забытый `next` — **ZOCOC002**.
Проглотить нижний — `[Replace]`. Две реализации на одном слое — ошибка реестра.
Подробности: скилл `zuloone-extend` §2б, вики `chain-of-command.md`.

## 2а. Платформенные контракты — один на слой, выше оборачивает

Кроме собственного `I<Имя>` сервис может реализовать контракт ПЛАТФОРМЫ
(`IQuantityConverter` и подобные) — платформа сама находит реализацию по
интерфейсу и зовёт её из своего кода.

**На одном слое реализующий должен быть ровно один.** Два сервиса одного
платформенного контракта на одном слое — исключение из реестра, и падает не
конвертация, а каждая затронутая операция платформы (для `IQuantityConverter` —
любая запись строки с количеством). На разных слоях это цепочка: верхний
зовёт `next` / `nextAsync`, если хочет оставить нижний в игре. Полная замена
на том же слое по-прежнему одним заходом: снести старый и завести новый.
Старый сервис живёт в базе и после удаления файлов —
`DELETE /api/services/{id}` плюс `DELETE /api/metadata/scripts/{id}`.

Требования платформенного контракта соблюдай буквально, они там не случайны:
- **не бросать исключений** из платформенного метода, если контракт велит
  возвращать `null` — «отказать в операции» решает платформа, а не сервис;
- **читать только через переданное соединение** (`request.Reader` и аналоги).
  Своё соединение внутри чужой транзакции промоутнет её в MSDTC (на Linux его
  нет), а `TransactionScope.Suppress` на SQL Server заблокируется на строках,
  залоченных текущей транзакцией: тест, посеявший данные внутри своего отката,
  ПОВИСНЕТ вместо падения.

## 2б. Код между моделями не переиспользуется

Наружу из модели торчит только СГЕНЕРИРОВАННЫЙ контракт — публичные
ИНСТАНС-методы. Статический помощник чужого сервиса не виден, унаследоваться
нельзя, общий базовый класс завести негде.

Отсюда практическое следствие: если одна и та же формула нужна в двух моделях,
её придётся продублировать. Это нормально для двух-трёх строк арифметики —
**но напиши в комментарии, что это осознанная копия и почему**, иначе следующий
читатель сочтёт это небрежностью и «исправит» одну из копий.

## 2в. Что можно возвращать наружу — контракт живёт в ОТДЕЛЬНОЙ сборке

Публичные методы сервиса дословно переписываются в интерфейс `I<Имя>`, и он
компилируется в СВОЮ сборку (`ZuloOne.Services.Contracts`) — **раньше моделей и
без доступа к коду скриптов**. Отсюда жёсткое правило:

**В сигнатуре публичного метода могут стоять только типы, видимые сборке
контрактов**: примитивы, `Guid`, `DateTime`, `decimal`, коллекции из них,
`Dictionary<string, object?>` и СГЕНЕРИРОВАННЫЕ сущности
(`.generated/Entities/`). Свой класс из файла скрипта — хоть вложенный, хоть
соседний — виден не будет.

Цена ошибки несоразмерна: сборка контрактов ЕДИНА на стенд, поэтому один DTO в
одной сигнатуре роняет компиляцию контрактов ВСЕХ сервисов — `models/compile`
покажет `Failed` на Core и `DependencyFailed` на всех моделях подряд, ни словом
не упомянув виновника. Настоящий диагноз даёт только
`POST /api/services/rebuild`: `Service contracts do not compile: CS0246
<ИмяТвоегоDTO>`.

Как правильно, если наружу просится составной результат:
- **результат надо хранить → возвращай `Guid` созданного ДОКУМЕНТА** (декларация,
  акт, расчёт — это документы, а не временные объекты: предъявляемое наружу
  обязано быть видно ровно в том виде, в каком отправлено, и замораживаться
  подтипом с `isReadOnly`);
- **результат эфемерный** → примитив или `Dictionary<string, object?>`;
- **набор полей на строку** → `List<(Guid Id, string Code, decimal Amount)>`:
  кортеж примитивов сборке контрактов виден, свой класс — нет;
- **сводные типы делай `private`** — приватные методы и типы в контракт не
  попадают, внутри считай чем удобно.

**У НОВОГО сервиса та же ошибка выглядит как «контракт не сгенерировался».**
`services/rebuild` скажет `Service '<Имя>' does not compile against its
contract: CS0234 ... 'I<Имя>' does not exist in the namespace
'ZuloOne.Services.Contracts'`, а `models/compile` — `CS0246 'I<Имя>' could not
be found` у ТОГО, КТО СЕРВИС ЗОВЁТ. Оба сообщения показывают пальцем на
отсутствующий интерфейс, и читается это как «платформа не успела его создать» —
тянет перезапускать контейнер и звать rebuild ещё раз. Интерфейса нет не
поэтому: генератор дошёл до публичной сигнатуры с невидимым типом и не смог
написать интерфейс ВООБЩЕ. Ищи в своих публичных методах свой же класс, а не
проблему с кэшем.

## 2г. Правило, охраняемое ДВУМЯ дверями, пишется ОДИН раз — здесь

Инвариант справочника часто проверяется дважды: обработчик не даёт завести
порчу, а сервис-потребитель отказывается считать, если порча всё-таки есть.
Обе двери нужны — но ПРЕДИКАТ у них обязан быть один, и живёт он в сервисе.

Продублируешь — границы разъедутся (`<=` против `<`, `.Date` против полного
времени), и справочник начнёт принимать расстановку, на которой расчёт падает.
То есть ошибку ввода снова ловит ОПЕРАЦИЯ — ровно то, ради чего проверку на
вводе и добавляли.

```csharp
// Сервис: правило + кто именно помешал (не bool — обработчику нужно имя).
public async Task<TaxRate?> FindOverlappingRateAsync(
    Guid tax, Guid excludeRate, DateTime from, DateTime? to) { ... }

// Обработчик: тонкая оркестровка, своего сравнения окон НЕТ.
var clash = await context.GetService<ITaxService>()
    .FindOverlappingRateAsync(record.Tax, record.MetaId, record.EffectiveFrom, record.EffectiveTo);
if (clash != null) return EventResult.Cancel($"...пересекается со ставкой «{clash.Code}»...");
```

`excludeRate` обязателен: при РЕДАКТИРОВАНИИ записи она сама попадёт в выборку
соседей и «пересечётся» с собой.

**Что это ломает в тестах.** Закрыв ввод, ты лишаешь интеграционный тест
возможности СОЗДАТЬ незаконное состояние и проверить второй рубеж:
`IDataService.InsertAsync` тоже поднимает `OnBeforeInsert` (сырой вставкой
объявлен только `RestoreAsync`, и он для восстановления удалённого). Проверяй
общий предикат прямо через сервис, а про непокрытый backstop честно напиши
комментарием — не подменяй покрытие `catch`-ем чего угодно.

## 2д. Что сервису доступно: крипта, JSON, внешние вызовы

Границу песочницы задают **два разных механизма**, и путать их дорого:

| | reference-набор `RuntimeCompiler` | deny-list `ScriptSecurityService` |
|---|---|---|
| что это | какие сборки видны компилятору | семантический анализ опасного API |
| отказ | `CS0103` / `CS0246` / `CS0012` | находка в проверке, отказ сохранения при Enforce |
| природа | **упущение**, если чего-то нет | **решение** |

Прежде чем проектировать «в обход запрета» — выясни, в каком из двух списков он
лежит. Криптографии и JSON не было в reference-наборе, и `CS0103: SHA256 does
not exist` читался как правило песочницы: из-за этого хеш саудовского счёта, CSR
и подпись QR жили в ЯДРЕ, то есть налоговый формат одной страны ехал внутри
платформы, которая ставится везде.

**Доступно сервису:**

```csharp
using System.Security.Cryptography;   // хеши, ECDSA, CertificateRequest, X509
using System.Text.Json;               // разбор ответа внешней системы
```

**Запрещено — и чем заменяется:**

| Запрещено | Вместо |
|---|---|
| `HttpClient`, сокеты, `WebRequest` | `IOutboundGateway.EnqueueAsync` (документ — в очередь) или `IOutboundCall.SendAsync` (одноразовый обмен) — по **имени канала**, не по URL |
| `ICredentialResolver` | назови имя credential; секрет подставит хост. Нужна подпись ключом хоста — `ICredentialSigner.SignHash(ref, hashBase64)`, вернёт подпись и публичную часть, но не ключ |
| `Process`, файловая система, `Reflection.Emit` | нет замены, и не должно быть |

Граница проходит **по секрету, а не по криптографии**: хешировать и подписывать
сервис умеет сам, прочитать настроенный ключ — нет.

**Логировать сервис тоже умеет** (частое заблуждение, из-за которого в дереве
заводятся пустые `catch`):

```csharp
ScriptServices.Get<ZuloOne.Log.IZuloOneLogger<МойСервис>>().Info("…", arg);
```

### Реализовать платформенный шов

Сервис может реализовать интерфейс ПЛАТФОРМЫ, и платформа его найдёт по этому
интерфейсу, а не по имени сервиса:

```csharp
public partial class FatooraSigner : IOutboundSigner
{
    public string Profile => "fatoora";
    public IReadOnlyDictionary<string, string> Sign(OutboundSigningContext context) => …;
}
```

Два способа поиска, и выбор не случаен:
- `ResolveImplementingAsync` — «кто ПЕРЕОПРЕДЕЛЯЕТ поведение»; две реализации в
  одном слое это неоднозначность, и она бросает;
- `ResolveAllImplementingAsync` — **набор по ключу**, где сосуществование
  нормально (профили подписи: по одному на страну).

Подробности: вики `wiki/developer/script-capabilities.md` и
`wiki/developer/outbound-integrations.md`.

## 3. Проверка

Рабочий цикл — **правки → компиляция → тесты**, рестарт ядра НЕ нужен: сборка
контрактов переиздаётся только когда исходники интерфейсов реально изменились
(сравнивается хэш), а кэши скомпилированных типов помечены поколением контрактов
и сами сбрасываются при их смене. Если всё же увидишь
`Unable to cast <Имя>Service to I<Имя>Service` — это перекос поколений, и это
БАГ платформы, а не повод перезапускать контейнер.

Специфично для сервисов:
- расширение чужого `I<Имя>` без `next` — `ZOCOC002` на Check и на `POST /api/services/rebuild`;
- контракты пересобираются при компиляции моделей — сервис со сломанным
  скриптом валит свою модель с понятной ошибкой;
- дизайнер «Сервисы» показывает генерённый контракт (Interface preview) и
  умеет вызвать метод кнопкой «Запустить» — быстрый ручной смок;
- та же полоска Chain of Command, что у событий: владелец слева, «Добавить
  свой поверх» создаёт обёртку с `next<T>` в рабочей модели; Check ловит
  `ZOCOC002`; колонка «Цепочка» в гриде, если имя живёт на нескольких слоях;
- интеграционный тест: `GetService<I<Имя>>()` + проверка результата метода;
- после любой правки сервиса подними `modelVersion` модели — иначе тенанты
  не зальют изменение.

Известное ограничение: контракты живут в памяти сервера — в плоской
IDE-сборке воркспейса (`dotnet build`) интерфейс `I<Имя>` не виден, сервисный
класс компилируется сам по себе, а ВЫЗОВЫ `GetService<I<Имя>>()` из других
скриптов IDE подсветит красным. Это ложный минус IDE, рантайм резолвит;
проверяй компиляцией моделей, не сборкой воркспейса.
