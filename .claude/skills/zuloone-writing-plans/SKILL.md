# План реализации

План пишется для исполнителя, который знает C#, но НЕ знает ни ZuloOne, ни
предметную область стенда. Всё, что ему нужно, — в плане: какой файл завести,
с каким `metaId`, в какой модели, как убедиться, что применилось.

**Объяви в начале:** «Пишу план по скилу zuloone-writing-plans».

## Когда план нужен

Не на всё. Одно поле на своём справочнике, один обработчик — бери сразу
`zuloone-new-*` и делай.

План обязателен, когда цена ошибки невозвратна:

- затронуто **больше одной модели** — направление зависимости и слой решаются
  один раз, переезд скрипта потом тянет за собой `metaId` и историю;
- новый **учётный контур** — документ + регистры + проводки + GL;
- меняется **проведение или состав движений** у работающего документа;
- **переименование/миграция** — переименование объекта создаёт НОВУЮ таблицу и
  бросает старую с данными;
- удаление чего-либо — удаления из файлов не распространяются, сносить надо
  через API с dry-run.

## Куда сохранять

`docs/plans/YYYY-MM-DD-<feature>.md` в корне воркспейса.

Не в папку модели: там хозяйничает экспорт. Синк отслеживает `.json`/`.cs`/`.vt`
— `.md` ему невидим, поэтому план в `docs/` живёт спокойно и попадает в git
рядом с кодом, который описывает. Бизнес-документация по итогу работы — отдельно,
в вики (`zulo.one/wiki/business/`), план туда не переезжает.

## Что решается ДО задач

Четыре решения, каждое из которых дорого переигрывать. Зафиксируй их в шапке
плана, иначе исполнитель примет их за тебя — наугад.

**1. Чья это модель и какой слой.** Скрипт принадлежит модели, чьими объектами
он командует. Ловушка в том, что регистры, константы и подтипы адресуются
**строкой**: `transactions.Add(new StockBalance { … })` через типизированный
класс компилятор проверит, а `RegisterMovementSpec("StockBalance")`,
`GlobalConstants` и `PostMovementAsync("…")` — нет. Поэтому модель может годами
писать в чужой регистр, и ни компиляция, ни гейт зависимостей этого не увидят.
В плане на каждый файл — модель-владелец, и проверка, что потребитель объявил
зависимость в своём `model.json` и слой это позволяет (`check_model_deps.py`).

**2. `metaId` выдаются в плане, а не по ходу.** Новый объект = новый uuid v4.
Это межзадачный контракт: задача 5 ссылается `edtMetaId` на EDT из задачи 2.
Сгенерируй GUID'ы сразу и сведи в таблицу шапки — иначе исполнитель придумает
свои, и ссылки не сойдутся.

**3. Строковые имена — в одну таблицу.** Имена аналитик регистра, констант,
подтипов, контрактов сервисов. Компилятор их не сверяет; расходятся они молча.
Отдельно: имя аналитики ≠ имя поля, правильное называет сама ошибка привязки
(`Bound: TaxCode, TaxDirection…`).

**4. Раскладка файлов диктуется видом объекта**, не вкусом: документ —
`<Модель>/Documents/<Имя>/<Имя>.object.json` + `Events/` + `Transactions/`,
справочник — `Dictionaries/`, тест — `Tests/`. Сверяйся с `zuloone-new-*`, не
изобретай структуру.

## Шапка плана

```markdown
# <Фича> — план реализации

**Цель:** одно предложение, что получится.
**Подход:** 2–3 предложения про архитектуру.
**ТЗ:** путь к спеке, из которой план выведен.

## Модели и слои
| Объект | Модель-владелец | Слой | Нужна зависимость |
|---|---|---|---|
| GoodsReceipt | Inventory | Solution(2) | Common ≥ 1.4.0 |

## metaId, выданные планом
| Объект | metaId |
|---|---|
| EDT ItemRef | 6f1c…-…-… |

## Строковые имена
| Что | Точное значение |
|---|---|
| Регистр | `StockBalance` |
| Аналитики | `Warehouse`, `Item` |
| Подтипы | `Draft` → `Received` |

## Общие требования
Версии, ограничения, правила именования — по одной строке, значения дословно
из ТЗ. Требования каждой задачи неявно включают этот раздел.
```

## Размер задачи

Задача — наименьшее, что несёт свой цикл проверки и что рецензент может
осмысленно отклонить отдельно от соседней. Настройку, скаффолдинг и доку
вкладывай в ту задачу, чьему результату они нужны. Каждая задача кончается
**наблюдаемым** результатом: тем, что можно увидеть `curl`'ом или прогоном.

## Шаблон задачи

````markdown
### Задача N: <что делаем>

**Файлы:**
- Создать: `Inventory/Documents/GoodsReceipt/GoodsReceipt.object.json`
- Создать ПАРОЙ: `…/Transactions/StockTx.script.json` + `StockTx.cs`
- Изменить: `Inventory/model.json` (бамп версии)

**Контракт:**
- Потребляет: `edtMetaId` = 6f1c… (задача 2), регистр `StockBalance`
- Отдаёт: документ `GoodsReceipt`, подтип `Received`, класс `StockTx`

- [ ] **Шаг 1. Написать файлы**

Полный json и полный C# — здесь, целиком, без «по аналогии».

- [ ] **Шаг 2. Синк применил**

```bash
docker logs zuloone-core-1 --since 2m 2>&1 | grep "Workspace sync"
```
Ждём `<файл> applied`. Тишина — не отказ, а гонка с экспортом: записать файл
заново. Пусто совсем — проверить гейт (`zuloone-verify` §0).

- [ ] **Шаг 3. Компиляция**

```bash
curl -s -X POST http://localhost:5257/api/metadata/models/compile
```
Все модели `Ok`.

- [ ] **Шаг 4. Схема** (если заводились объекты или поля)

```bash
curl -s -X POST http://localhost:5257/api/schema/sync
```

- [ ] **Шаг 5. Тест** — `Tests/<Имя>.json` + `<Имя>.cs`, `groupName` обязателен

```bash
curl -s -X POST http://localhost:5257/api/metadata/tests/<GUID>/run
```

- [ ] **Шаг 6. Бамп `modelVersion`** в `Inventory/model.json`: 1.3.0 → 1.4.0

- [ ] **Шаг 7. Коммит — ОБЕ половины скрипта**

```bash
git add Inventory/Documents/GoodsReceipt/Transactions/StockTx.script.json \
        Inventory/Documents/GoodsReceipt/Transactions/StockTx.cs
git commit -m "feat(inventory): приход пишет движения склада"
```
````

## Тест-первый: где работает, а где самообман

Красный тест до реализации в ZuloOne возможен **не всегда**, и различие ровно в
том, по имени идёт обращение или по типу.

- **Харнес `Db` адресует строками** — `CreateDocumentAsync("GoodsReceipt", …)`,
  `QueryBalancesAsync("StockBalance", …)`. Такой тест КОМПИЛИРУЕТСЯ до того, как
  объект заведён, и падает в рантайме осмысленно. Это честный красный — с него и
  начинай задачу.
- **Типизированный доступ** — `GetRecordAsync<Item>`, `GetDocumentAsync<T>`,
  сущность в транзакционном скрипте — требует сгенерированного класса. До
  появления объекта это `CS0246`: не «тест упал», а «скрипт не собрался», и
  разницы между «логика не написана» и «опечатка в имени» такой красный не
  показывает. Типизированные проверки дописывай ПОСЛЕ того, как объект в базе.
- Новый **документ** сущность получает только после `docker restart
  zuloone-core-1` — `schema/sync` и компиляция не помогают. Заложи перезапуск
  отдельным шагом, а не «почему-то не видит».

Сверх этого действуют правила `zuloone-new-test`: тест обязан уметь падать
(сними защиту, прогони, верни), а побочный эффект проведения заводится
ПРИХОДОМ, не `PostMovementAsync` — прямое движение не запускает драйверы.

## Без заглушек

Это провалы плана, не мелочи:

- «добавить поле» без полного json: `metaId`, `edtMetaId`/`baseType`,
  `length`/`precision`. Целое — `Integer`; `Int` импорт проглотит молча, а
  упадёт `schema/sync`;
- «сослаться на EDT» без его `metaId`;
- «написать проводки» без строки `transactions.Add(new …)`;
- «аналогично задаче N» — повтори код, задачи читают вразнобой;
- «добавить валидацию», «обработать краевые случаи»;
- файл без указания модели-владельца;
- шаг, результат которого никак не наблюдаем.

## Самопроверка

Прогони сам, без субагента. Нашёл — чини на месте и иди дальше.

1. **Покрытие ТЗ** — на каждый пункт спеки указывается задача.
2. **Заглушки** — поиск по списку выше.
3. **`metaId`** — каждая внутренняя ссылка ведёт либо на GUID из таблицы шапки,
   либо на объект, уже существующий в воркспейсе.
4. **Строковые имена** — аналитики, константы, подтипы совпадают с таблицей
   посимвольно.
5. **Бамп** — у КАЖДОЙ затронутой модели есть шаг с `modelVersion`. Расширяешь
   чужой объект — бампаешь свою модель, не чужую.
6. **Зависимости** — потребитель объявил её в `model.json`, слой позволяет.
7. **Имена классов** — уникальны во всём воркспейсе: второе звено цепочки несёт
   суффикс (`<Имя>ExtEventHandler`, `<Имя>Tx_<Модель>`).
8. **Пары файлов** — у каждого скрипта в коммит-шаге обе половины.

## Исполнение

План сохранён — предложи два способа:

**1. Задача за задачей в этой сессии** — после каждой задачи полный цикл
`zuloone-verify`, отметка чекбоксов по ходу.

**2. Субагент на задачу** (`Agent`) — свежий контекст на каждую, ревью между.
Годится для задач, которые НЕ трогают стенд (разметка файлов, json).

**Стенд общий и один.** Параллельные субагенты, гоняющие тесты, засоряют друг
другу прогон: чужие метаданные с восьмизначным хвостом валят компиляцию `Core`,
а за ней все модели. Задачи, доходящие до `tests/run-all`, исполняй
последовательно. Мести — `POST /api/dev/test-artifacts/sweep`.

Пакетная заливка больше 25 файлов за вызов отклоняется целиком — дроби.
