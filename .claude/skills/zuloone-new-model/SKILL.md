# Новая модель

Модель — единица поставки бизнес-слоя (аналог модели D365FO): папка верхнего
уровня воркспейса со своими метаданными, кодом и меню. Всё, что ты создаёшь,
живёт в какой-то модели.

## 1. Папка и манифест — `<Имя>/model.json`

```json
{
  "kind": "Model",
  "object": {
    "modelType": "Custom",
    "description": "<Что это за модуль — одним предложением>",
    "modelVersion": "1.0.0",
    "publisher": "<Издатель>",
    "isSystem": false,
    "isSealed": false,
    "isEnabled": true,
    "metaId": "<НОВЫЙ GUID модели>",
    "name": "<Имя>",
    "modelId": "00000000-0000-0000-0000-000000000000",
    "layerId": 2
  },
  "dependencies": []
}
```

- `name` — PascalCase латиницей (`WMS`, `CRM`, `PayrollUA`).
- `modelId` у самой модели — нули (модель сама себе корень); у всех ЕЁ объектов
  `modelId` = `metaId` модели.
- `modelVersion` — semver: patch — фиксы кода, minor — аддитивные изменения,
  major — ломающие.
- **Слой (`layerId`) — по роли модели**, и он определяет, кто кого может
  расширять (расширения смотрят только вниз):
  | layerId | Слой | Кто кладёт сюда модели |
  |---|---|---|
  | 0 | System | только платформа (Core) — не для тебя |
  | 1 | Base | базовые прикладные модели продукта |
  | 2 | Solution | отраслевые/партнёрские решения (ISV) |
  | 3 | Customization | кастомизации внедрения (VAR) |
  | 4 | User | локальные доработки конкретного стенда |

## 2. Зависимости — ОБЯЗАТЕЛЬНЫ

Если модель использует хоть что-то из другой модели — ссылочный EDT на её
справочник, проводку в её регистр, поле-расширение или скрипт на её объекте,
пункт меню в её группе — зависимость ДОЛЖНА быть объявлена:

```json
"dependencies": [
  {
    "modelMetaId": "<GUID ЭТОЙ модели>",
    "dependsOnModelMetaId": "<GUID модели-зависимости>",
    "minVersion": "1.0.0",
    "name": "<Имя>-><ИмяЗависимости>",
    "metaId": "<НОВЫЙ GUID>",
    "modelId": "<GUID ЭТОЙ модели>",
    "layerId": 2
  }
]
```

Почему это не формальность:
- порядок компиляции моделей — топологический по зависимостям; без ребра
  твои скрипты могут компилироваться раньше чужих сущностей;
- падение зависимости помечает твою модель `DependencyFailed`, а не даёт
  загадочную ошибку;
- перенос на другой стенд (бандл/git) проверяет зависимости и `minVersion`
  ДО импорта — без объявления модель приедет сломанной;
- включение/отключение моделей валидируется по графу.

Правила:
- зависимость от **Core не объявляется** — ядро есть на каждом стенде,
  его версия = версия приложения;
- слой модели ≥ слоя каждой её зависимости (Solution может зависеть от Base,
  но не наоборот);
- циклы запрещены.

## 3. Стартовый скелет

Стандартные подпапки создаются по мере надобности (пустые не нужны):
`Dictionaries/ Documents/ Registers/ TableParts/ EDTs/ Enums/
NumberSequences/ Scripts/ Commands/ Services/ Jobs/ Tests/ Menu/ Forms/
Translations/`.

Сразу после model.json:
1. **Меню модели** — `Menu/menu.json` с корневой группой модели (бесшаблонные
   пункты видны всем поверх любого шаблона; можно прививаться в чужую группу
   через `parentMetaId` — это тоже зависимость!). Под корневой группой сразу
   заведи ПОДГРУППЫ ПО ВИДУ ОБЪЕКТА — `Dictionaries`/«Справочники»,
   `Documents`/«Документы», `Registers`/«Итоги», `Reports`/«Отчёты» (это тоже
   `targetType: "Group"` с `parentMetaId` = корневая группа модели). Заводи
   только те, что реально понадобятся — пустые ribbon сам не покажет, но и
   плодить впрок не нужно. Один уровень вложенности — ровно то, что рисует
   риббон (группа-вкладка → подгруппа-колонка → пункты); подгруппа внутри
   подгруппы уже не рендерится колонкой. Пункты объектов (шаг 2) цепляются
   `parentMetaId` к СВОЕЙ подгруппе по виду, а не к корневой группе напрямую.
2. Первые объекты — скилами `zuloone-new-dictionary` / `new-document` /
   `new-register`.
3. Проверка — `zuloone-verify` (модель должна компилироваться `Ok` уже пустой).

## 4. Жизненный цикл

- На дев-стенде модель из файла создаётся включённой (`isEnabled: true`).
- К клиенту модель едет бандлом или git clone + import-all — приезжает
  ВЫКЛЮЧЕННОЙ; включение — отдельное валидируемое действие (зависимости,
  конфликты полей, лицензия).
- `isSealed: true` — модель запечатана издателем: на стенде её правят только
  расширениями из моделей выше.
